Avishkaar is a visual-first, community-verified discovery platform for **offbeat tourism, regional cuisines, and local heritage**. It pairs a Pinterest-style masonry feed of photos and short vertical clips with AI-structured guides — and ranks everything by an explainable **Hidden Gem Score** instead of mainstream popularity, so lesser-known places surface on merit and community trust, not clickbait.

---

## Highlights

**Discovery**
- Masonry feed of photos and short vertical clips (hover-to-play previews, YouTube Shorts embeds) across **40 seeded real offbeat destinations**
- **Hidden Gem Score** on every card, with a full breakdown popover explaining exactly how the score was earned
- **Detour Bar** — *"Instead of X, Go Here"*: top-3 lower-crowd alternatives for crowded hotspots
- Leaflet/OpenStreetMap map view with custom vector markers

**Trust & community**
- **Vouches** and **Verified Visit check-ins** (GPS, 25 km haversine radius) drive ranking — not likes
- Tier system — *Wanderer → Pathfinder → Local Legend* — gates who can volunteer as a local guide
- **Community-verified safety advisories**: published by trusted tiers or after community verification, hidden when flags outnumber verifies
- Impact drawer showing each traveller's contribution; milestone badges

**AI-structured guides**
- Every place carries a structured guide — commute, food, activities, **Living Heritage**, and safety — generated by **Gemini (strict JSON mode)** from a traveller's raw notes and photo, in multiple languages
- Zero-commission vendor actions that support local businesses directly
- Deterministic multilingual fallback extractor when no Gemini key is configured — the demo never breaks

**Experience & design**
- Cinematic **monolith-style preloader** (wordmark, cycling destination photos, live progress, curtain reveal) with a logo handoff into the navbar
- Full-screen hero landing gate, paper-textured reading canvas, regional card tones
- Wine Red (`#6B1D2F`) design language · Rozha One display type · SF Pro body · Modak for Hindi
- Custom SVG icon set, Memoji-style avatars, scroll progress bar, offline pocket cards

## Quick start — Demo Mode (no keys needed)

```bash
npm ci
npm run dev        # http://localhost:3000
```

With no env vars set, the app runs in **Demo Mode**: 40 seeded destinations, 6 demo personas (switchable in one click from the account menu), and a local JSON demo store. This is the mode for local development and live judging.

```bash
npm test           # domain + API/security tests
npx tsc --noEmit   # typecheck
npm run lint       # ESLint (flat config)
npm run build      # production build
npm start          # production server
```

## Modes

| | Demo Mode | Supabase Mode |
|---|---|---|
| Enabled when | No `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Both are set |
| Data | `.data/demo-store.json` (local) or `/tmp` on serverless | Supabase PostgreSQL (5 tables) |
| Auth | Persona switcher (scoped to demo UI), body `userId` trusted **in development only** | Supabase Auth (email + Google), verified Bearer tokens, profiles synced on OAuth sign-in |
| Persistence | **Ephemeral by design** — the demo store is a JSON file, lost on serverless cold starts. Not production storage. | Durable |

> **Production safety:** in `NODE_ENV=production`, Demo Mode auth is refused unless `DEMO_MODE=true` is set explicitly — a deploy that forgot its Supabase env vars fails closed instead of trusting client-supplied user IDs.

## Environment variables

Copy `.env.example` to `.env.local`:

| Variable | Required | Notes |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase mode | Project URL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Supabase mode | Anon key |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase mode (server) | Server-side only, never expose to the client |
| `GEMINI_API_KEY` | No | Without it, a deterministic multilingual fallback extractor is used |
| `GEMINI_MODEL` | No | Default `gemini-2.5-flash` |
| `DEMO_MODE` | No | Set `true` only to intentionally run Demo Mode in production |
| `ALLOW_DEMO_CHECKIN` | No | Set `true` on a judging deployment to enable the simulated GPS check-in in production. In development it is always available. Real check-ins use browser geolocation within a 25 km haversine radius. |

## Supabase setup

1. Create a Supabase project.
2. Run `supabase/migrations/0001_init.sql` — 5 tables (`profiles`, `places`, `vouches`, `user_badges`, `guide_requests`), RLS policies, atomic `vouch_place` / `check_in_place` / `verify_safety_alert` / `award_milestone_badges` RPCs, `place-media` storage bucket, auto-profile on signup.
3. Set the env vars above.
4. Seed demo data: `npm run seed`

## Core mechanics

- **Hidden Gem Score** = `((Vouches × 2) + (Verified Check-ins × 5)) / log10(Mainstream Popularity Index + 10)` — shown with a full breakdown on every card.
- **Vouch** = +10 Trailblazer points to the place's author; **Verified Visit Vouch** (check in first, then vouch) = +25. You cannot vouch for or check in to your own place.
- **Tiers:** Wanderer (0+) · Pathfinder (100+) · Local Legend (300+). Only Pathfinder+, Local Legends, or verified locals can volunteer as guides.
- **Safety advisories** become public when authored by a Pathfinder+, or after 2+ community verifies; 2+ flags that outnumber verifies hide an alert.
- **Detour Bar:** top-3 lower-crowd alternatives for crowded hotspots (Gemini vibe match when configured, deterministic fallback otherwise).
- **Uploads:** authenticated only; file type is detected from magic bytes (JPEG/PNG/WebP/GIF, MP4/WebM) — SVG/HTML and spoofed types are rejected. Images ≤ 25 MB, video clips ≤ 8 MB.
